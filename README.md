# Code Version Manager（工作空间版本管理）

独立的 Git 图形版本管理器，可管理任意工作空间，支持本地离线发布和远程仓库同步。

主要功能：

- 为尚未使用 Git 的目录启用版本管理
- 工作空间位于其他 Git 仓库内时，仍可创建独立版本库
- 记录最近打开的 10 个工作空间，可从标题栏快速切换，点击每条记录右侧的 × 单独移除，或清空全部记录
- 首次启用时只显示工作空间第一层，勾选目录会递归封装其内容
- 发布后续版本时同样只显示第一层；已删除的顶层文件和整个目录继续显示并默认勾选，记录所选范围内的删除
- 发布版本时自行勾选要封装的文件
- 配置 Git 提交姓名、邮箱和 SSH 远程仓库，支持生成或使用已有 SSH 密钥同步
- 在软件内创建、切换本地和 origin 分支；开发分支可创建带分支命名空间的预发布标签
- 以 Git 三方合并将开发分支合入 main，使用 Beyond Compare、Meld 或 KDiff3 解决冲突
- 按当前分支筛选正式版和预发布版，继承的正式版本只读；删除已合并分支时可单独选择清理其预发布标签
- 发布版本只保存到本地；“同步本地”以远程分支和版本标签为准，“同步远程”以本地为准
- 同步前显示本地领先、远程领先或双方分叉，以及提交时间、说明和本次操作会造成的更新、回退、新增或删除
- 本地恢复点保留同步前分支、标签及版本清单；远程旧引用会先下载到本机恢复点
- 支持 `v0.0.1`、`v1.7.8.5`、`v1.7.8.9.7` 等多段版本号
- 版本历史按多段版本号从新到旧排序，不受文件日期影响
- 查看版本历史和版本标签
- 手动修改已发布版本的修改说明，并同步更新 Git 标签和 CHANGELOG
- 使用 Beyond Compare、Meld 或 KDiff3 比较两个完整版本目录
- 选择一个历史版本，使用已配置的对比工具与完整当前工作空间比较并修改当前文件
- 在标题栏“设置”中选择当前工作空间使用的对比工具，默认使用 Beyond Compare
- Beyond Compare 每次比较都加载软件内置的 `BCSessions.xml` 默认配置：按文件大小比较、关闭时间戳和内容快速比较、启用 Unicode 规范化，排除 `.git`、`*.zip` 和 `__pycache__`，目录树默认折叠
- 任意选择一个历史版本并下载为 ZIP，默认文件名为 `工作空间名_版本号.zip`（如 `m9_ws_v1.2.0.zip`）
- 删除所选版本标签，不改写提交历史或删除工作空间文件
- 删除 main 的最新版本及 Git 提交，分支退回上一提交并保留文件和已有暂存内容
- 在窗口底部显示当前 Git 增量版本历史占用的磁盘空间
- 查看或下载自动生成的版本管理 `CHANGELOG.rst`，查看窗口支持一键最大化和还原
- CHANGELOG 使用标准 RST 标题格式，每行改动自动输出为 `* 内容`
- 启用版本管理时补充根目录 CHANGELOG 模板和 Git 忽略规则，发布时按版本号提取手写说明
- 可按工作空间开启 VERSION 自动同步，发布时更新版本号并纳入版本包
- 工具元数据保存在 `.git/code-version-manager/`
- 在历史版本状态下阻止误提交
- 通过窗口标题栏的“关于”按钮查看当前软件版本

## 分支版本与合并

Git 标签是仓库级引用。GitHub 的 Tags/Releases 页面始终列出整个仓库的标签，不能按网页当前选择的分支隐藏标签。软件用带分支前缀的预发布标签标明开发来源，并在本地版本历史中筛选；前缀只区分标签归属，不改变 GitHub 页面范围。

- **main** 只创建正式版本标签，例如 `v0.3.1`。下一正式版本按仓库已有正式版本递增。
- **开发分支** 只创建自己的预发布标签。当前正式版为 `v0.3.0` 时，`test1` 的默认下一个版本为 `test1/v0.3.1-beta.1`；后续预发布在同一分支依次递增。Git 中的标签名为 `branches/test1/v0.3.1-beta.1`；分支名含 `/` 时会编码以确保唯一。旧的未加分支前缀的 `v0.x` 标签保留为正式版，不迁移。
- 主窗口的“版本历史”范围默认为“本分支相关版本”，显示当前分支自己的标签和它继承的正式版本；继承的正式版本标记为“只读”，仍可比较和导出。选择“全部分支版本”会显示仓库内其他分支标签。修改或删除正式标签时，如果其他活动分支仍包含该提交，软件会阻止操作。

以 `test1` 从 `v0.2.0` 开始开发、main 继续发布到 `v0.3.0` 为例：在 `test1` 发布 beta 标签；完成后点击“合并到 main”，选择 `test1`。软件获取 `origin/main` 与 `origin/test1`，本地落后时安全快进，本地领先时保留本地提交。两端已经分叉时会停止，不会重置或覆盖任何一端。

合并要求工作区干净，并由 Git 使用 `--no-ff` 保留两边提交历史。无冲突时合并会直接完成；有冲突时切换、发布和同步会暂停，主窗口显示冲突文件。选择文件后可打开“设置”中配置的 Beyond Compare、Meld 或 KDiff3；工具关闭后，检查结果并点击“标记已解决”，全部解决后点击“完成合并”。也可以点击“取消合并”恢复开始合并时的 main。对比工具负责产生文件合并结果，Git 负责记录冲突解决和合并提交。

新增、删除或特殊文件冲突会提示手动处理：保存最终内容后“标记已解决”，或明确选择“以删除解决”。未安装合并工具或取消工具时，冲突状态保留，软件不会把工具退出自动视为解决。

合并完成后，在 main 使用“发布正式版本”创建 `v0.3.1` 并按需“同步远程”。`v0.3.0` 仍指向原提交；合并不会移动或改写它。只有已经完全合入 main 的开发分支才能删除。删除对话框会列出本地和远程将处理的引用；默认保留开发标签归档，可选一并清理对应分支前缀的预发布标签。删除分支本身不会删除它的标签。

## Git 账号与远程同步

远程同步统一使用 SSH；本地仓库路径也可用于同步。配置界面包含 SSH 仓库地址、提交姓名和邮箱，推送超时放在“Git 账号”的高级设置中；对比工具通过标题栏“设置”配置。0.2.0 起发布版本只保存到本地，移除自动同步选项；旧版启用的自动同步配置也不再触发上传。

1. 在 GitHub、Gitee、GitLab 或其他 Git 服务上先创建远程仓库，并确保 SSH 密钥所属账号具有写入权限。GitHub 可点击“Git 账号”中的“创建远程仓库（网页）”，在官方网页登录并确认创建。
2. 打开工作空间，点击“Git 账号”。软件优先填入该工作空间的 `origin` 地址，并将 GitHub 的 HTTPS 地址转换为 SSH。例如，本项目的地址为 `git@github.com:lqxmb/code-version-manager.git`。没有 `origin` 时，按工作空间目录名显示地址示例；请填写真实的 GitHub 账号或组织，确认远程仓库名，再填写提交姓名和邮箱。自定义 SSH 主机别名和端口按系统 SSH 配置使用。
3. 点击“SSH 公钥设置”复制本机 `.pub` 公钥。没有密钥时，可在此窗口输入邮箱和可选口令，点击“生成新的 SSH 密钥”；成功后直接复制新公钥，在 GitHub 中选择 `Authentication Key`、粘贴并保存。私钥保存在本机，不会显示或上传。
4. 点击“保存并验证连接”。本地已有提交时会对当前分支和可达版本标签执行不上传版本的 Git 推送 dry-run；也可以只保存配置，离线发布后再刷新检查远程状态。
5. 发布版本只创建本地版本。差异检查完成后，主窗口会显示当前分支哪边领先。点击“同步本地”以远程为准，或点击“同步远程”以本地为准；确认框固定左侧本地、右侧远程，列出提交时间、说明和将要改变的分支及版本标签。

提交姓名和邮箱仅用于记录作者，SSH 身份由系统密钥决定。仓库地址、作者信息和超时选项保存在当前工作空间的 Git 本地配置中，不修改其他仓库或全局配置。保存配置会更新当前仓库的 `origin` 并清除旧的单独推送地址和自动同步选项，其他远程不受影响。尚未启用版本管理的工作空间会先创建独立本地仓库。

发布、配置和同步按钮的作用：

| 按钮 | 作用 | 结果反馈 |
| --- | --- | --- |
| 发布正式版本 / 发布预发布版本 | main 创建正式标签；开发分支创建分支专属预发布标签，均仅保存在本地 | 状态栏显示完整标签归属 |
| 保存配置 | 保存当前工作空间的仓库地址、作者信息和超时设置，不访问远程 | 状态栏提示已保存、尚未验证连接；同步按钮暂时禁用 |
| 保存并验证连接 | 先保存配置，再检查读取连接和推送权限，不上传版本 | 成功弹窗显示“连接及推送预检查通过”；失败弹窗显示原因 |
| 主窗口的“同步本地” | 将本地当前分支和所属标签变为远程状态 | 确认框列出本地将被替换或删除的引用；未提交修改会先保存，完成后可恢复 |
| 主窗口的“同步远程” | 将远程当前分支和所属标签变为本地状态 | 确认框列出远程将被替换或删除的引用；远程旧引用先保存到本机恢复点 |

首次配置或修改地址、密钥后建议验证连接，无需每次发布前重复验证。尚无本地提交或正在查看历史提交时，只能检查读取权限，弹窗会显示“连接成功，推送尚未验证”。发布首个本地版本或返回工作分支后可再次验证。预检查通过后，正式同步仍需满足分支保护规则和服务端检查。

### 同步方向和状态

| 背景和文字 | 含义 | 是否可点击 |
| --- | --- | --- |
| 红色“同步本地” | 当前分支或所属标签与远程不同，远程分支可读取 | 点击后查看差异并确认，让本地引用以远程为准 |
| 红色“同步远程” | 当前分支或所属标签与远程不同，写入预检查通过 | 点击后查看差异并确认，让远程引用以本地为准 |
| 绿色按钮 | 当前分支和所属标签与远程一致 | 禁用，无需同步 |
| 默认背景且禁用 | 远程不可读、查看历史版本，或远程端拒绝同步 | 鼠标悬停查看各方向原因 |
| 正在检查 | 正在读取远程引用或其他操作进行中 | 暂时禁用 |

打开工作空间、刷新、发布或修改本地版本、完成任一方向的同步后，软件会在后台重新检查。检查会读取远程引用；本机缺少远程提交数据时会下载到 Git 对象库，用于显示提交详情和判断先后关系，因此首次检查可能需要等待下载，已下载的对象会复用。检查不上传或删除内容，不修改分支、版本标签或工作区文件。网络问题修复后点击标题栏的“刷新”。

0.2.7 起，同步确认窗口会直接显示新旧关系和本次操作的结果：

| 显示内容 | 含义 |
| --- | --- |
| 本地较新，领先远程 N 个提交 | 本地包含远程提交并增加了 N 个提交；同步远程可补入这些提交，同步本地会回退本地当前分支 |
| 远程较新，领先本地 N 个提交 | 远程包含本地提交并增加了 N 个提交；同步本地可补入这些提交，同步远程会回退远程当前分支 |
| 双方已分叉 | 两边都有独有提交，无法简单判断哪边更新；确认窗口显示各自的提交数 |
| 代码提交相同，标签信息不同 | 同名版本标签指向同一个代码提交，标签说明等信息存在差异 |
| 仅本地存在 / 仅远程存在 | 另一边没有该分支或版本标签，不能单凭存在与否判断新旧；窗口提示本次会新增还是删除标签 |
| 暂时无法判断新旧 | 提交历史不完整或详情无法读取，可核对提交信息或取消后刷新重试 |

新旧关系按 Git 提交历史判断，时间和版本号仅供核对；未提交的工作区修改不参与新旧判断。分支领先也不表示所有版本标签一致，执行前仍需查看各标签的操作说明。

同步范围是当前工作分支和归属于它的标签：main 同步正式标签，开发分支同步其命名空间内的预发布标签。开发分支继承的正式版本用于查看，首次接入远程分支时会补齐可追溯的正式标签，开发分支的同步不会改写或删除它们。其他开发分支的标签和非版本标签不参与。共享正式标签若会被改写或删除，会禁用对应方向；补齐缺失标签仍然允许。以远程为准时，软件创建本地 Git 恢复引用，并备份版本清单及 CHANGELOG；未提交修改和未跟踪文件会先保存到恢复点，再更新当前分支和所属标签，完成后可从弹窗恢复。可能被远程目标覆盖的被忽略文件会移到恢复点，不会直接删除。以本地为准时，软件先将远程旧分支和所属标签下载到本地恢复引用，再用带精确租约的原子推送更新或删除远程引用。远程检查后有协作者更新时，租约校验会拒绝覆盖。

分支下拉框每个分支只显示一行：`main（当前，本地和 origin 均有）` 表示本地和远程都有同名引用，`feature（本地）` 表示只有本地分支，`test1（origin，仅远程）` 表示远程独有分支。选择同名分支时优先切换本地分支；选择远程独有分支时才下载并建立本地跟踪分支。

“同步远程”会重写当前远程分支并替换或删除当前分支所属且通过共享检查的版本标签，可能影响其他协作者。正式版标签是仓库级引用；删除它会让所有分支都不再有该标签，所以若其他活动分支仍包含它，软件会阻止删除。恢复点保存在本地 Git 元数据中，不是远程备份。远程仓库不包含软件私有的版本清单；操作前本地清单和 CHANGELOG 会另存于 `.git/code-version-manager/recovery/`，远程标签本身不包含该清单。

### SSH 密钥与连接

- 已有密钥时，直接在“SSH 公钥设置”中选择并复制公钥。不要上传或发送没有 `.pub` 后缀的私钥。
- 没有密钥时，直接在“SSH 公钥设置”中输入邮箱，点击“生成新的 SSH 密钥”。邮箱默认取自账号窗口中填写的提交邮箱，用作密钥备注；密钥口令可选，设置时需输入两次确认。软件调用本机 `ssh-keygen` 生成 Ed25519 密钥，默认保存在 `~/.ssh/id_ed25519` 和 `~/.ssh/id_ed25519.pub`，同名文件已存在时自动使用 `id_ed25519_cvm_数字`，不会覆盖已有文件。也可自行在终端执行 `ssh-keygen -t ed25519 -C "你的邮箱"`。
- 加密私钥需先用 `ssh-add ~/.ssh/id_ed25519` 解锁；使用自动生成的新文件名或自定义文件名时，也需先用 `ssh-add` 加载，界面会显示对应命令。口令只用于本次生成，不保存在配置中。软件不会改写系统 SSH 配置。
- 首次连接 GitHub 时，在终端运行 `ssh -T git@github.com`，核对官方主机指纹后确认，不要关闭主机密钥检查。显示 `Hi <账号>! You've successfully authenticated` 表示身份验证成功；该测试命令通常返回退出码 1。
- `Permission denied (publickey)` 表示需要检查公钥授权、SSH agent 或所选密钥；远程写入被拒绝时还需检查该账号的仓库写权限和分支规则。修复后点击“刷新”，再选择同步方向。

### 远程还没有仓库

“创建远程仓库（网页）”会根据填写的 GitHub 地址预填仓库名和拥有者；地址留空时使用工作空间名称，拥有者在网页选择。页面建议创建私有仓库，公开性和拥有者仍需在网页确认。软件不会静默创建、覆盖仓库或自动上传文件。

在网页中登录后确认创建。请勿初始化 README、`.gitignore` 或许可证，避免与现有本地提交产生不同历史。创建完成后把 SSH 地址填回软件并验证、同步；已有仓库不必重复创建。此网页入口仅支持 GitHub，其他平台请先在对应网站创建仓库。

### 远程操作超时

连接、读取仓库和推送预检查的超时为 120 秒；实际推送分支和版本标签默认允许 15 分钟，可以在“Git 账号 → 高级设置：推送超时”中设置为 1–60 分钟。SSH 同步仍可能因大文件或网络缓慢长时间等待，因此仍保留此设置，一般使用默认值即可。设置仅保存到当前仓库的本地 Git 配置，不影响其他仓库。同步状态栏显示已等待时间，超时提示区分连接和推送阶段，并保留 Git 最后输出。

超时会终止本次 Git 及其传输子进程，恢复网络后点击“刷新”重新比较两端状态，再选择同步方向。超时不能确认远程是否已接收更新。如果长时间没有进度，请检查本机网络、代理或 VPN。

### 失败后的补同步

- 发布始终只创建本地提交和版本标签。断网、认证失败、远程拒绝写入等情况不影响本地发布，也不会删除本地文件。
- 本地连续发布多个正式版或预发布版后，可“同步远程”一次补齐当前分支及其所属标签。继续发布的新版本仍只保存在本地。
- 正式标签保持 `v0.3.1`；开发标签使用 `branches/<编码分支名>/v0.3.1-beta.1`，不会覆盖其他分支的同名 beta 标签。
- 远程同步使用原子推送应用本次引用变更，远程服务必须支持原子推送；本地同步前备份引用和工作区修改，失败时可使用恢复点。
- 同名标签存在差异时，只有通过共享正式标签保护检查才允许按所选方向更新。同步远程会使用精确引用租约保护远程并发更新；同步本地会验证取回对象与检查结果一致。
- 远程同步上传完整 Git 提交历史，不仅是本次勾选的文件，也不只包含 ZIP 导出范围；同步前请确认历史中没有不应公开的内容。软件私有的版本清单和 CHANGELOG 仍保存在 `.git/code-version-manager/`，不会作为工作空间文件上传。

## 工作空间 CHANGELOG 与 VERSION

首次启用版本管理并发布首个版本时，根目录缺少 `CHANGELOG.rst` 就创建带 RST 示例注释的空模板，已有内容保留。缺少 `.gitignore` 时生成默认模板，排除 Catkin 普通及隔离构建产物、VS Code 本地设置、日志、缓存、编辑器临时文件、ZIP 和根目录 CHANGELOG；已有 `.gitignore` 则只追加 `/CHANGELOG.rst`，保留其他规则。新增或修改的 `.gitignore` 自动纳入首个版本。先配置 Git 账号创建空仓库、再发布首个版本时同样适用。打开或刷新已有仓库不会自动创建这些文件。

根目录 `CHANGELOG.rst` 可作为手动编写发布说明的参考，也作为工具栏“下载 CHANGELOG”的目标文件；下载会将 Git 标签生成的历史记录写入该文件，已有文件时会先询问是否覆盖。它不纳入新版本提交、封装清单或 ZIP。已被 Git 跟踪的根目录 CHANGELOG 在下次发布时停止跟踪，本地文件和历史提交保留。按下面格式编写目标版本节：

```rst
0.2.9 (2026-11-02)
------------------
* 新增功能
* 修复问题
```

打开发布窗口时，软件按窗口中的版本号读取对应节的列表条目。修改版本号后，匹配到对应节就替换窗口说明，未匹配则保留当前内容。标题可以带 `v`，支持多段版本号；日期不必与实际发布日期一致。窗口中的说明可继续编辑，最终按窗口内容发布。发布、修改历史说明或删除版本都不回写根目录 CHANGELOG。工具栏的“查看 CHANGELOG”和“下载 CHANGELOG”使用由 Git 版本标签生成的历史记录；下载会直接保存到工作空间根目录。

“发布时生成并同步 VERSION 文件”可在发布窗口或“设置”中开关，配置保存在当前仓库。未配置时，根目录已有 `VERSION` 默认开启，没有则默认关闭。开启后，发布前将 `VERSION` 写为不带 `v` 的最终版本号并换行，例如 `0.2.9`，自动加入提交、封装清单和 ZIP，无需勾选该文件。保存设置不会立即创建或修改 VERSION；关闭后按普通文件手动管理。若 VERSION 被忽略规则排除，需移除该规则或关闭同步后再发布。发布提交失败时会恢复 VERSION 原内容，未选中文件的暂存状态继续保留。

## 发布时记录删除

0.2.4 起，已有暂存内容不会阻止发布。新版本按勾选范围记录工作区当前内容，未勾选文件的暂存状态保留。已经暂存的删除也会显示为“已删除”，无需先取消暂存。

如果上一版本已经提交了 `.vscode/`，之后在 `.gitignore` 中添加 `/.vscode/`，再次发布时会自动停止跟踪这些文件，并从新版本的 Git 提交和封装清单中移除，本地文件保留。发布窗口会提示将停止跟踪的文件数量，鼠标悬停可查看路径。这项操作按当前忽略规则应用于所有已跟踪文件，不受封装勾选范围限制。已有版本和历史提交仍保留原来的文件；同步远程后，新版本才会反映这次移除。

删除 main 的最新版本及提交时，当前文件会保留。若已有暂存内容，退回时会保留整个暂存区，被删除提交的改动也会成为暂存中的修改；若暂存区为空，被删除提交的改动会保留为未暂存修改。

0.2.3 起，发布文件列表会保留已经删除的顶层文件和目录，并标记“已删除”、默认勾选。保留勾选后，删除操作会写入新版本的 Git 提交和标签；也可以只选择已删除项发布版本。

旧版仅扫描仍存在的文件，整个顶层目录或文件被删除后会从发布列表消失，导致删除未提交。ZIP 按本机封装清单导出，而 Git 标签和 GitHub 仍保留旧文件，因此同一版本可能出现不同文件清单。升级后发布新版本时，勾选这些已删除项即可修正新版本；已经发布的旧标签需要另行修正，升级本身不会改写已有版本。

## 构建 VERSION 安装包

构建脚本自动读取项目目录下的 `VERSION`（假如当前为 `0.2.9`），替换 `debian/control` 模板中的 `@VERSION@`，生成安装包的版本信息。以后升级只需修改 `VERSION`，然后执行打包：

```bash
# 在 code-version-manager/ 目录中执行
sh build_deb.sh
```

生成的安装包为 `dist/code-version-manager_$(cat VERSION)_all.deb`。

安装前先关闭正在运行的版本管理器。需要卸载旧版时可执行（直接升级无需卸载）：

```bash
sudo apt remove code-version-manager
```

在项目目录中执行以下命令安装或升级：

```bash
sudo apt install ./dist/code-version-manager_$(cat VERSION)_all.deb
```



安装前需要的软件和完整安装步骤请查看 [INSTALL.md](INSTALL.md)。
版本变更记录请查看 [CHANGELOG.rst](CHANGELOG.rst)。
使用 `apt install` 安装时，APT 会自动检查并安装缺少的必需依赖。

安装后从应用菜单打开 `Code Version Manager`。
